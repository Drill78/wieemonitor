## 2. 关键决策与理由

### 2.1 为什么选 Next.js（App Router）

- **全栈一体**：前端页面、后端 API、静态资源都在一个项目里，单进程部署即可，无需额外管理后端服务。
- **TypeScript 原生支持**：前后端共用类型定义，避免接口失配。
- **App Router**：服务端组件可以直接读数据库，减少 client-side fetch 往返；客户端组件按需 `'use client'`，与地图（必须在浏览器跑）配合自然。
- **部署简单**：自托管模式下 `npm run build && npm run start` 就能跑，无需复杂的部署流水线。
- **生态成熟**：插件、文档、社区都比较丰富，遇到问题好查。

### 2.2 为什么选 Leaflet（react-leaflet）而不是 Mapbox / 高德 / Cesium

| 选项 | 不选的理由 |
|------|------------|
| Mapbox GL JS | 商业授权，超过免费额度需要付费；底图依赖 Mapbox 服务（外网） |
| 高德地图 JS API | 强制使用 GCJ-02 坐标系，与 WGS84 数据来源冲突；需要 Key；对外网依赖 |
| 百度地图 | 同上，且坐标系是 BD-09，问题更多 |
| Cesium / 三维 | 当前阶段不需要 3D，引入复杂度过高 |

选 Leaflet 的理由：

- **开源、免费、轻量**
- **底图灵活**：可以用 OpenStreetMap，也可以将来自建瓦片服务（如 OSM Tile 缓存）
- **WGS84 原生**
- **react-leaflet 封装良好**，与 React 生态契合
- **离线友好**：将来如果单位内网无外网，可以把瓦片下载到本地服务

### 2.3 为什么选 PostgreSQL + PostGIS

- **PostGIS 是 GIS 领域事实标准**：空间索引（GiST）、空间函数（ST_Within, ST_Distance 等）开箱即用。
- **样线（LineString）、保护区（Polygon）、相机点位（Point）** 都可以原生存储为 `geometry` 类型。
- **空间查询性能好**：例如"查找某保护区内所有相机"、"查找某样线 200 米范围内的相机"都是一句 SQL。
- **开源、跨平台**，可以在同一台 Windows / Linux 机器上跑。
- 备选方案 SQLite + SpatiaLite 太轻，未来扩展不方便；MongoDB 的 GeoJSON 支持不如 PostGIS 严谨。

### 2.4 为什么不部署到 Vercel

- **数据量大**：图片可能几十 GB 起，Vercel 的存储 / 带宽配额不够。
- **本地文件访问**：Vercel 的 Serverless 函数无持久文件系统，图片必须放对象存储（S3 / R2），与"自托管 + 本地文件"的现实冲突。
- **数据库**：需要 PostGIS，Vercel 默认数据库不支持，需要外接 Supabase 等服务，反而增加复杂度。
- **数据敏感性**：野外采集数据可能涉及保护区敏感坐标，不适合放第三方云。

### 2.5 数据存储策略

> **核心原则：数据库存元数据 + 坐标 + 文件路径；二进制文件存磁盘。**

- **数据库里**：
  - 表元数据（保护区名、样线名、相机编号、采样时间、物种鉴定等）
  - GIS 几何（PostGIS 的 `geometry(SRID=4326)`）
  - 文件路径（相对路径，例如 `camera-photos/2024/SXBHQ-001/IMG_0001.jpg`）

- **磁盘里**：
  - 原始照片、音频文件
  - 按年份 / 保护区 / 相机编号分层存储
  - 备份策略：定期 rsync 到外接硬盘 / NAS

- **不做**：
  - 不把图片塞进数据库（`bytea` 性能差、备份大）
  - 不依赖云对象存储（与"自托管"冲突）

### 2.6 坐标系决策

- **数据库存储**：WGS84（EPSG:4326），PostGIS 几何字段统一用 `SRID=4326`。
- **前端展示**：Leaflet 默认 Web Mercator（EPSG:3857）做投影显示，但传入的经纬度仍是 WGS84，Leaflet 自动处理。
- **数据导入**：原始 shapefile / GPX / Excel 如果不是 WGS84，导入脚本里要做一次转换（用 `proj4` / `ogr2ogr`）。

### 2.7 前后端在同一个 Next.js 项目里

- **API Routes**：放在 `src/app/api/.../route.ts`，作为 BFF 层（Backend For Frontend）。
- **服务端组件**：可以直接调 ORM / 数据库，不必都走 API。
- **不引入额外的后端框架**（如 NestJS / Express），保持单仓库、单进程、单部署。
- 将来如果有重型计算（如声音特征提取、图像识别），再考虑独立 Python worker，通过队列与主应用解耦。

## 4. 拒绝引入的复杂度

以下方案在当前阶段**明确不引入**，避免过度设计：

- ❌ Kubernetes / 微服务
- ❌ GraphQL（REST + 类型共享已够用）
- ❌ Redux / Zustand 等全局状态库（React 自带 + URL 参数足够）
- ❌ 服务端渲染优化（SSR / ISR 调优）
- ❌ 多语言 i18n（先做中文版）
- ❌ 移动端 App（先做 Web，响应式自适应）
